La HU-18 detecta anomalías sobre `pedidos` y los eventos de HU-19. Los umbrales iniciales son X = 24 h, Y = 4 h y Z = 2 h, expresados en horas enteras de 1 a 168. La llegada a oficina y la confirmación de recepción son acciones distintas. La modificación de parámetros requiere autorización DBA y una sesión individual de operador para registrar al responsable.

| Criterio | Implementación |
| --- | --- |
| CA-1 | Permanencia continua en la misma oficina. Un registro repetido en esa oficina no reinicia el plazo. |
| CA-2 | Exige una parada pendiente asignada. Se toma el evento más reciente entre la asignación, el historial, las ubicaciones, las incidencias y los checkpoints aplicados. |
| CA-3 | La escucha transaccional de Envíos y Rutas genera la alerta al registrar el segundo fallo. Reutiliza el contador de `Pedido.registrarIncidencia`. El job también reconstruye la alerta de datos anteriores. |
| CA-4 | Una llegada de HU-19 inicia Z. La confirmación explícita del operador detiene esa condición. |
| CA-5 | X, Y y Z residen en la BD. Cada evaluación los consulta. El cambio usa versión esperada y guarda auditoría. |
| CA-6 | Panel con filtros, paginación, detalle operativo y cierre manual auditado. |
| CA-7 | Clave única por envío, tipo y evento, más una restricción que permite una sola alerta activa por envío y tipo. Se conserva el evento cerrado para impedir su regeneración. |
| CA-8 | Endpoint específico de alertas accesible al remitente o destinatario autenticado. El banner se actualiza cada 30 segundos. |
| CA-9 | Teléfono validado en backend y frontend, enlace `tel:` y contacto general configurable como alternativa. |
| CA-10 | Cierre automático al desaparecer la condición. La consulta del cliente vuelve a comprobarla, por lo que oculta alertas obsoletas incluso antes del siguiente job. |

El job evalúa lotes de 100 pedidos, con un máximo permitido de 500. Un límite superior de identificador fija el conjunto a recorrer en cada ejecución. Una fila bloqueada en una conexión dedicada excluye otras instancias durante la ejecución. Las reglas usan transacciones independientes, con bloqueo del pedido, y un fallo en una regla conserva las demás evaluaciones. El bloqueo se libera al cerrar o perder la conexión. El pool debe disponer de al menos tres conexiones para atender el job y peticiones simultáneas.

Los umbrales usan comparación estricta. Exactamente X, Y o Z horas todavía no genera una anomalía. Los registros nuevos de HU-18 usan `Instant`, un reloj UTC inyectable y columnas `TIMESTAMP WITH TIME ZONE`. Los eventos antiguos de HU-19 guardan fechas sin zona. `ANOMALIAS_ZONA_HISTORICA` define cómo interpretarlos y debe coincidir con la zona del servidor que los escribió. El valor inicial es UTC, compatible con un servidor que haya escrito esas fechas en UTC. Las incidencias del contador existente ya usan UTC.

Los envíos pausados y los que salen de los estados logísticos activos dejan de generar alertas. Al reanudar, el historial de reanudación cuenta como nuevo evento para la inactividad. La permanencia mide tiempo natural desde la entrada a la oficina. Los eventos corregidos de HU-19 se excluyen cuando existe su reemplazo. La oficina responsable procede del último evento válido con oficina registrada. Si todavía no existe uno, el cliente recibe el contacto general.

| Método y ruta bajo `/api/v1` | Acceso y comportamiento |
| --- | --- |
| `GET /pedidos/anomalias` | Operador. Filtros `estado`, `tipo`, `pagina` y `tamano`, máximo 100 registros. |
| `GET /pedidos/anomalias/{id}` | Operador. Evidencia estructurada y auditoría del cierre. |
| `POST /pedidos/anomalias/{id}/cierre` | Operador. `estado` admite RESUELTA o DESCARTADA y `origen` usa lista cerrada. Repetir el mismo cierre es idempotente. Cambiar un cierre terminal responde 409. |
| `GET /pedidos/anomalias/recepciones-pendientes` | Operador. Llegadas vigentes sin confirmar, 20 por página. |
| `POST /pedidos/{id}/recepcion-oficina` | Operador. Exige `eventoLlegadaId` del último evento del mismo pedido y etapa LLEGADO_OFICINA_DESTINO, más `origen`. Repetir la confirmación conserva el primer registro. |
| `GET /pedidos/anomalias/parametros` | Sesión individual de operador y cabecera DBA válida. |
| `PUT /pedidos/anomalias/parametros` | Igual autorización. Exige X, Y, Z, versión esperada y origen. Una versión desactualizada responde 409. |
| `GET /pedidos/mios/tracking/{tracking}/alertas` | Cliente remitente o destinatario autorizado. Cada alerta contiene únicamente mensaje, oficina, teléfono y enlace de llamada. |

El panel está en `/panel/alertas`, enlazado desde el menú del operador. Incluye la bandeja de recepción y el formulario protegido de parámetros. El formulario mantiene la clave DBA en memoria durante la operación y la limpia al guardar o abandonar la pantalla. Las alertas del portal se integran en la vista existente de seguimiento del cliente.

Las siguientes reglas de seguridad se aplican al alcance nuevo de HU-18.

| Regla solicitada | Cumplimiento y alcance |
| --- | --- |
| 1. RBAC | `SecurityConfig` exige Operador para administración operativa. Los servicios vuelven a verificar el rol y su perfil. Parámetros requieren adicionalmente la clave DBA. Las sesiones autenticadas con un rol incorrecto reciben 403. Una sesión ausente o vencida recibe 401, conforme al sistema existente. |
| 2. Autorización de objeto | `AccesoClientePedido` comprueba remitente o destinatario antes de consultar las alertas. La confirmación exige la llegada vigente del mismo pedido. Los operadores conservan el ámbito global de operación existente, porque el repositorio no asigna operadores a oficinas. |
| 3. Validación | DTOs con Bean Validation y `SoloCamposDeclarados`, reutilizando la lista blanca existente. Enumeraciones cerradas, paginación limitada, teléfono normalizado y SQL parametrizado. Los cuerpos que intentan asignar campos adicionales se rechazan. |
| 4. Salida segura y CSRF | React presenta textos como contenido escapado y valida el teléfono antes del `href`. No se introduce HTML de usuario. La API conserva autenticación stateless con Bearer explícito y sin cookies de sesión. La clave administrativa también viaja en una cabecera explícita. |
| 5. Errores y logs | Los endpoints nuevos usan errores genéricos. El motor registra únicamente el tipo de regla y la clase de fallo. No imprime cuerpos, SQL, claves, tokens ni detalles de excepciones. |
| 6. Minimización | Las alertas almacenan IDs operativos, marcas temporales, umbral e intentos. No almacenan descripciones libres, nombres de personas, documentos, correos o direcciones. Se reutiliza la protección de identidad existente sin copiar esos datos. |
| 7. Auditoría | Cambios de parámetros con usuario, fecha UTC, origen y versión. Los cierres manuales y las recepciones guardan usuario, fecha UTC y origen. El cierre automático identifica origen SISTEMA y deja el usuario nulo. La creación de alertas corresponde al motor automático. |
| 8. Concurrencia e idempotencia | Restricciones únicas en BD, bloqueo del pedido, bloqueo distribuido del job y transacciones. Confirmaciones repetidas y cierres idénticos conservan el primer registro. Parámetros usan versión esperada. |
| 9. Secretos y dependencias | DBA y contacto general se configuran en el entorno. No se añaden dependencias de producción. La verificación E2E usa Playwright y Psycopg con versiones fijas en `scripts/requirements-hu18-e2e.txt`. Las identidades y autorizaciones de las pruebas son sintéticas. |
| 10. TLS y rate limiting | Las peticiones nuevas reutilizan el origen HTTPS del despliegue. Debe mantenerse TLS en Render y entre servicios según la configuración del entorno. Se aplica un límite compartido en BD de 60 operaciones por usuario y minuto para los endpoints nuevos, incluidas consultas de alertas. Al excederse devuelve 429. Las pruebas locales usan HTTP en loopback. |

Para activar el cambio, Identidad debe aplicar `V28__anomalias_y_recepciones.sql` antes de habilitar la función en Envíos y Rutas. `ANOMALIAS_ENABLED` está activado por defecto y permite deshabilitar temporalmente las escuchas, el job y los endpoints durante un despliegue escalonado. El frontend incorpora el banner, por lo que debe publicarse cuando las APIs estén disponibles.

La migración V1 ya contenía una tabla `anomalias` ligada a `envios` y `eventos_logisticos`, que el backend actual de pedidos no consume. V28 la conserva íntegra con el nombre `anomalias_legacy_hu18` y crea la tabla nueva vinculada a `pedidos`. No existe una correspondencia demostrada entre los IDs del modelo antiguo y los del actual, por lo que los registros históricos se conservan sin atribuirlos a pedidos por suposición. Cualquier consulta externa directa a la tabla antigua deberá usar el nombre histórico.

| Variable | Configuración |
| --- | --- |
| `ANOMALIAS_ENABLED` | Activación de HU-18 en Envíos y Rutas. Valor inicial true. |
| `DBA_API_KEY` | Debe configurarse también en Envíos para proteger el formulario de parámetros, usando el mismo mecanismo administrativo existente. |
| `ANOMALIAS_CONTACTO_GENERAL` | Teléfono real de atención de la empresa, preferiblemente en formato internacional. Debe configurarse para que el fallback pueda iniciar una llamada. |
| `ANOMALIAS_ZONA_HISTORICA` | Zona usada para interpretar timestamps antiguos de ubicación e historial. Inicial UTC. |
| `ANOMALIAS_LOTE` | Lote del job. Inicial 100. Rango de 1 a 500. |
| `ANOMALIAS_INTERVALO_MS` | Demora entre recorridos. Inicial 60000 ms. |

Queda pendiente proporcionar el teléfono general de la empresa. Hasta que se configure, una alerta cuya oficina tampoco tenga un teléfono válido muestra el canal general como texto y omite el enlace de llamada. También queda pendiente verificar la configuración efectiva de TLS y los datos históricos en el entorno Render. El job necesita un proceso activo. Si una instancia entra en suspensión, la evaluación se reanuda cuando el servicio vuelve a ejecutarse. Las pruebas de esta entrega se ejecutan en bases locales aisladas, con datos sintéticos.

Las pruebas JUnit se ejecutan con el wrapper Maven existente en Envíos y Rutas. `AnomaliasReglasTest` comprueba los límites exactos y los teléfonos maliciosos. `AnomaliasIntegracionTest` recorre las APIs con sesiones reales, incluyendo acceso ajeno, roles incorrectos, clave DBA ausente, límites, campos adicionales, auditoría, confirmación, cierre, deduplicación y concurrencia. `AnomaliasPostgresTest` se activa cuando existe `HU18_TEST_POSTGRES_URL`, junto con `HU18_TEST_POSTGRES_USER` y `HU18_TEST_POSTGRES_PASSWORD`, y crea esquemas temporales para verificar la migración, las restricciones y la exclusión entre conexiones.

Para el E2E de navegador, construir el JAR de Envíos mediante `bash mvnw package -DskipTests`, ejecutar `npm ci` en el frontend, instalar las herramientas con `python -m pip install -r scripts/requirements-hu18-e2e.txt` y descargar Chromium con `python -m playwright install chromium`. Después configurar `HU18_E2E_POSTGRES_DSN` hacia una instancia PostgreSQL local de pruebas y ejecutar `python scripts/hu18_portal_e2e.py` desde el repositorio. El script crea un esquema aislado, aplica todas las migraciones, genera sesiones y autorizaciones efímeras, inicia backend y frontend, prueba el portal y elimina el esquema. `HU18_JAVA_BIN` permite seleccionar un Java compatible y `HU18_CHROMIUM_BIN` permite reutilizar un Chromium ya instalado. Los registros temporales quedan en `HU18_E2E_LOG_DIR` o en el directorio temporal del sistema.

La validación local final completó 661 pruebas en Envíos y 654 en Rutas, sin fallos. Las cuatro pruebas PostgreSQL se ejecutaron expresamente contra PostgreSQL 16.4. También pasaron la aplicación completa de V1 a V28, la compilación TypeScript/Vite, ESLint y el recorrido E2E con backend y PostgreSQL reales. El E2E verificó el portal a 390 px, la aparición y cierre de alertas, la recepción, las llamadas de oficina y del contacto general, el bloqueo de envíos ajenos, los textos escapados y los cambios auditados de umbrales. Estas validaciones corresponden a un entorno local aislado.
